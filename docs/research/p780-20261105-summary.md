# P780 设备实测总结：A 槽写入与切槽失败（2026-11-05）

对象：Rakuten Hand 5G / TINNO P780（holi / SD480，Android 11，5.4.233，SPL 2024-02-01，
adb 序列号 `b940328a`）。本轮设备实验已停止，设备当前正常从 **B 槽**启动。

## 1. 结论摘要

1. **A 槽写入成功**：自建 OTA 证书 + 自签 52.8 MB 多分区 payload 被 update_engine 接受，
   `boot`/`vendor_boot`/`vbmeta` 三个分区全部写入 A 槽，`Completed 3/3 operations`，
   `ErrorCode::kSuccess`。
2. **切槽失败**：重启后仍为 `_b`。`SetActiveBootSlot(A)` 没有改变 ABL 的选择。
3. **ABL 判据是 GPT 属性，不是 misc**：
   - GPT 在 `/dev/block/sde`，**4096 B 扇区**，header 0x1000，entries 0x2000；
   - `boot_a` attributes `0x00b2000000000000`（priority 2），
     `boot_b` attributes `0x007f000000000000`（priority 15）；
   - 用 init 域写 misc 的 `bootloader_control`（`fd=23`，CRC 正确）后重启，仍然进 B。
4. **写 GPT 的权限只在 `hal_bootctl`**：
   - init 打开 `/dev/block/sde` O_WRONLY 返回 **-13 EACCES**；
   - untrusted_app 读 `/vendor/lib64/libboot_control_qti.so` 返回 EACCES；
   - shell / system_app 执行 `bootctl set-active-boot-slot a` 均报
     `Error getting bootctrl v1.0 module`。
5. **全局 libc++ `_Znwm` hook 不可行**：只重放 `_Znwm` prologue 的 stub 稳定；
   任何带栈保存、`getpid`、`openat`、TLS tid 读取或 GPT 写入的变体都会在数秒内整机重启。
   原因是 `_Znwm` 在极早期/敏感上下文被调用，全局 hook 影响所有进程。

## 2. 本轮新增能力


### 2.4 GPT 解析结果

| 分区 | entry 偏移 | attributes |
|---|---|---|
| boot_a | 0x2400 | `0x00b2000000000000` |
| vbmeta_a | 0x2580 | `0x103b000000000000` |
| vendor_boot_a | 0x2900 | `0x0400000000000000` |
| boot_b | 0x2d80 | `0x007f000000000000` |
| vbmeta_b | 0x2f00 | `0x107f000000000000` |
| vendor_boot_b | 0x3180 | `0x0400000000000000` |

按 bit 48–51 priority、52–55 tries、56 successful 解码：
A priority=2，B priority=15。

### 2.5 misc 实测

- init 域 `openat("/dev/block/by-name/misc", O_WRONLY)` 成功（fd=23）；
- 写入 32 B `bootloader_control`：magic `0x42414342`、version 1、
  `slot_info[0]=0x6f`、`slot_info[1]=0x0e`、CRC32 覆盖前 28 B 写偏移 0x1c；
- 重启仍为 `_b`。

### 2.6 libc++ `_Znwm` detour 尝试

`/system/lib64/libc++.so` 可被 app 页写；`_Znwm` 在 0x4eb54。尝试：

| stub 内容 | 结果 |
|---|---|
| 仅重放 `_Znwm` 前 16 B prologue | 稳定 |
| 加栈保存/恢复 | 重启 |
| 加 `getpid` 门禁 | 重启 |
| 加 `openat("/dev/block/sde")` | 重启 |
| 读 `tpidr_el0+0x10` 作为 tid 门禁 | 重启 |
| 纯寄存器 + open/pwrite GPT | 重启 |

结论：全局 libc++ hook 不能用于该目标。

## 4. 边界

- 没有验证 A 槽能否实际启动：切槽未发生，无法启动 A；
- A 槽写入的是 **stock B 内核**，不是 Magisk/root 镜像；
- `SetActiveBootSlot` 未修改 GPT，ABL 仍选 B；
- 没有 EDL 写通道；本轮没有修改 GPT，设备 GPT 主备一致；
- 全局 libc++ hook 的失败是实测边界，不证明 hal_bootctl 域不可进入，只证明当前
  `_Znwm` 方案不可行。

## 5. 如果需要继续

优先级从高到低：

1. 找 **HAL 专属 hook 点**（`libboot_control_qti.so` 的 `SetActiveBootSlot` 或
   HAL 二进制的 binder 入口），而不是全局 libc++；
2. 找一个 **能读 vendor 文件且能执行 IPsec 页写**的域（例如 system_app 下用
   `app_process` 跑自带 helper），把 gadget 注入 hal_bootctl；
3. 若拿到 hal_bootctl 代码执行，直接 pwrite GPT：`boot_a` →
   `0x007f000000000000`，`boot_b` → `0x0070000000000001`，并重算 entries/header CRC
   （本轮已离线算好：entries `0xc103a961`，header `0x9c9e68d5`）。
