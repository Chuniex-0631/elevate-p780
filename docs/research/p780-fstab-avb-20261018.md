# P780 fstab AVB 挂载配置实机取证（2026-10-18）

**证据类型：用户通过普通 ADB shell 提供的两个文件文本（会话附件），已核对 5 行 AVB 挂载声明。并非原始 fstab 文件字节哈希或实际 Bootloader vbmeta.img 的签名描述符。**

## 输入及出处

用户执行：
```powershell
adb shell cat /vendor/etc/fstab.default
adb shell cat /vendor/etc/fstab.emmc
```
两者均成功显示内容；此前 `/vendor/etc/fstab.qcom` 不存在。现有附加会话文本保存了完整 fstab 输出，本专题只记录与 AVB 有关的派生摘要，避免把聊天复制当作文件系统原件。

## 两份文件共同的 AVB 规则

| 逻辑分区 | fs_mgr flags 中的 AVB 项 | 其它关键 flags | 证据支持 |
|---|---|---|---|
| `system` | `avb=vbmeta_system` | `slotselect,logical,first_stage_mount` | 配置把系统级验证目标命名为 `vbmeta_system` |
| `system_ext` | `avb=vbmeta_system` | 同上 | 与 system 同一声明的 VBMeta 名称 |
| `product` | `avb=vbmeta_system` | 同上 | 与 system 同一声明的 VBMeta 名称 |
| `vendor` | `avb` | `slotselect,logical,first_stage_mount` | 普通 AVB 路径，没有写成 `avb=vbmeta_system` |
| `odm` | `avb` | `slotselect,logical,first_stage_mount` | 普通 AVB 路径，没有写成 `avb=vbmeta_system` |

两份 fstab 对以上五个分区**完全一致**，与本轮此前实测的 `vbmeta_b→/dev/block/sde31`、`vbmeta_system_b→/dev/block/sda11`、B 槽五份 dm-verity 节点**相容并构成独立的配置层交叉证据**。仍缺 `vbmeta_b` 真正的 `Chain Partition Descriptor`、公钥和 `vbmeta_system_b` 内容，**不能由 fstab 配置直接证明根 vbmeta 的密码学授权或具体哈希算法/钥匙**。

特别是 `vendor/odm` 的裸 `avb` 表示 fs_mgr 经由默认 AVB 句柄设立 verity，不等于已从根 VBMeta 镜像确认它们的真实 hashtree descriptors。另一个限制是：这两份文件当前在 `/vendor/etc` 可读取，并不独立证明设备在第一阶段启动时究竟选择哪个 fstab 文件或是否使用 Boot ramdisk/device tree 中的另一个配置。要提升到运行时确定性，须有经验证的 init 选择来源或者离线固件源。

## GSI 附加公钥路径：不可与生产 Root of Trust 混同

两份文件的 `system` 行还有：

```text
avb_keys=/avb/q-gsi.avbpubkey:/avb/r-gsi.avbpubkey:/avb/s-gsi.avbpubkey
```

这是适用于 GSI / DSU 的额外已信任公钥文件候选，**不是**固件出厂 `vbmeta_b` 根公钥的已验证指纹，也不是 AVB 私钥。AOSP [first_stage_mount.cpp](https://chromium.googlesource.com/aosp/platform/system/core/+/refs/heads/master/init/first_stage_mount.cpp) 明确写到：如果同一挂载项有 `avb_keys` 和 `avb` 两种标志，会优先尝试独立的 VBMeta / 这些 key，失败时回退默认 `avb` 路径。即使这些 .avbpubkey 文件确实存在，它们也不能直接证明可用它们刷入替代系统或绕过 locked Bootloader。

## 其它差异

`fstab.default` 的 `/data` 加密配置采用 `v2+inlinecrypt_optimized+wrappedkey_v0`；`fstab.emmc` 的对应标志为 `v2+emmc_optimized+wrappedkey_v0`。**这只是配置差异**，文件名含 `emmc` 或 `/misc` 的 fs type 标为 `emmc` 都不足以推翻此前块设备与硬件资料中 UFS 的实机记录。

```text
No OTA URL found for your build. Either Google does not recognize your build fingerprint, or there are no new updates for your device.
```
