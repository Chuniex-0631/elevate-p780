# AVB 链重审：根/系统链都是公开测试密钥（2026-10-26）

> 2026-10-28 文档复核：只更正解释与证据范围，未新增设备实测；当前状态以 [STATUS](../STATUS.md) 为准，历史候选步骤不作为当前执行计划。

> 2026-10-26 审计更正：本页为历史探索记录。后续[离线控制流复核](p780-boot-edl-audit-20261026.md)确认注册表与 FRP 读取，但未建立 FRP→菜单隐藏的完整链；“FRP 门控为0”“retail无工厂镜像”“唯一阻塞”等推论未证实。misc 实际使用换行分隔，不是点号。不要执行本页历史建议的 misc/boot/vbmeta 写入；此次任务仅离线审计。

> 本轮只做离线核对与两次低风险 fastboot 验证，**没有写任何分区**。
> 结论：本机 AVB 的**根 vbmeta 和 vbmeta_system 都由 AOSP 公开测试私钥签名**；
> 密钥身份核验不证明可写、可切槽或可启动；早期 DSU key/版本解释为历史假设，后续仍未形成可用启动链。

## 1. 本地已核验的密钥事实

| 层 | 算法 | 公钥 SHA1 | 对应私钥 | 状态 |
|---|---|---|---|---|
| `vbmeta_a/b`（根） | SHA256_RSA4096 | `2597c218…` | `09/testkey_rsa4096.pem`（AOSP 公开） | 模数逐位相同（49 号已验） |
| `vbmeta_system_a/b` | SHA256_RSA2048 | `cdbb7717…` | `09/testkey_rsa2048.pem`（AOSP 公开，本轮下载） | **模数逐位相同（本轮新验）** |

`vbmeta_system` 里有 `system` / `product` / `system_ext` 的 hashtree 描述符；
也就是说 **system 链也是 AOSP 公开测试密钥**。

## 2. 这改变了什么

- 之前 09/13/14 的 DSU 实验：
  - 用 **RSA4096 root testkey** 重签 GSI；
  - 或用 Google **Android 15 / Q Developer** GSI（`e53f344b…`）。
- 本机是 **Android 11（R）/ VNDK30**，`vbmeta_system` 用的是 **RSA2048 testkey**，
  而 GSI 的 first-stage 走 `/avb/{q,r,s}-gsi.avbpubkey`。
- **正确的实验变量**应是：
  1. 先读 first-stage ramdisk 里的 `q/r/s-gsi.avbpubkey`，确认 GSI 到底信任哪把 key；
  2. 选 **Android 11 R GSI**（不是 Android 15），签名/key 与 whitelist 对齐；
  3. 再走 DSU。
- 如果 GSI key 就是 AOSP `testkey_rsa2048`，私钥是公开的，可自签 R GSI；
  如果是 Google R GSI key，则用官方 R GSI。

## 4. 历史推荐顺序（已暂停）

1. **完整 boot dump（49 MB，6×8 MiB chunk）**：用 48 号 init 域读块设备原语；
   读 first-stage ramdisk 的 `/avb/*.avbpubkey`、fstab、init，确认 GSI key。
   只读，不写分区。
2. **Android 11 R GSI + DSU**：按正确的 key/版本安装；boot 后是 userdebug，
   可 `adb root`/`su`，拿到 root GSI。
3. **若 root**：用 `09/testkey_rsa4096.pem` 重签 boot、用 `testkey_rsa2048.pem`
   重签 `vbmeta_system` 是历史候选；写入、设备端 AVB、切槽与修改后镜像启动均须另验，不能记为持久 Root。
4. **ABL/XBL dump**：init 域读 `abl`/`xbl`/`xbl_config`/`devcfg`，离线找隐藏
   fastboot 命令、EDL/工厂模式；20 号说的“没有 abl.img 无法判断”可以补上。
5. **GhostLock 5.4.210**：有公开完整 5.4 实现（ARM32），但 P780 有
   `CFI_CLANG`/`PAN`/`PXN`/KASLR，栈 shellcode 不能直接搬；作为备用内核线。

## 5. 产物

## 6. 完整 boot dump 与 GSI key（2026-10-26）

用 48 号 init 域读块设备原语，把 `boot_b` 完整拉下：

- 镜像 51,408,896 B（7 个 8 MiB chunk，最后一个只取前 1,077,248 B；其余是分区 padding）；
- boot header v3：`kernel_size=41,767,424`、`ramdisk_size=9,630,085`、`page_size=4096`；
- ramdisk gzip 解压后 22,276,352 B、443 个 cpio 条目；
- 产物：`boot_b_full.img`、`boot_b_full_unpacked/`（`ramdisk.cpio` + `root/`）。

**first-stage GSI 公钥**（`first_stage_ramdisk/avb/`，各 1032 B，RSA4096）：

| 文件 | SHA-256 |
|---|---|
| `q-gsi.avbpubkey` | `07b37325316fd483765d474aafcaca908b4de4773e16ed87aed415c15f71fb98` |
| `r-gsi.avbpubkey` | `4706b8d2ffd46c5759d9431b8bf95f5c0544f4f6c87bbe35ff591325eb1783f5` |
| `s-gsi.avbpubkey` | `ec60e13d92331e2c2d5d1372a5d7f2131861dc602815fd87c0637d14790b4538` |

三把都是**不同的 RSA4096 key**，且都**不等于** AOSP root testkey
`7728e30f…`，也不等于 RSA2048 的 system testkey。也就是说：

- 之前用 **Q Developer Android15**（系统公钥 `e53f344b…`）：不是 `q-gsi 07b373…`；
- 之前用 **root testkey_rsa4096** 重签：不是 `r-gsi 4706b8…`；
- 已核对的候选 GSI key 不匹配；实际启动失败阶段仍不能仅由离线 key 比较完整还原。

历史曾假设官方 Android 11 R GSI 与本机 r-gsi 匹配；后续核对未支持该假设，见 §7。版本对齐不能替代公钥核对或设备端启动验证。

|---|---|---|

| GMS `gsi_gms_arm64-exp-RP1A.200720.009` | `e53f344beb2646b49651ea8dd336dbe75117183e96ef34beed4b367a4a0ae925`（Q Developer） | `4706b8d2…` |

两条 GSI 都是 **Q Developer key `e53f344b…`**，不是设备的
`q/r/s-gsi`（`07b373…` / `4706b8…` / `ec60e1…`）。也就是说：

- 已核对候选与设备 GSI 公钥不同；不能仅凭差异确定密钥所有者为 OEM/TINNO；
- 已测试/离线核对的 GSI 未形成启动链；不能扩展到所有 Google GSI，也不能仅据此确定历史失败的唯一原因；
- 当前未取得匹配已记录 GSI 信任链的可用候选；密钥归属、其它兼容路径与设备端失败阶段不得仅由这些摘要推断。

**DSU/GSI 线关闭。** 剩余方向：ABL/XBL dump 找隐藏 factory/EDL/unlock 入口，
或内核写（GhostLock 5.4）→ 写 boot/vbmeta（root/system 是公开 testkey，
boot 的签名不是障碍）。

## 8. ABL/XBL dump 与门控（2026-10-26）

四个分区已用 init 域读块设备原语完整拉下：

| 分区 | 大小 | 内容 |
|---|---|---|
| `abl_b` | 1,048,576 | ELF32 包装 + UEFI FV；LZMA 在 0x3078，解出 434,376 B 的 AArch64 PE |
| `xbl_b` | 3,670,016 | **EDL/Sahara/DLOAD** 明文 |
| `xbl_config_b` | 131,072 | 配置，无明文关键字 |
| `devcfg_b` | 131,072 | 配置，无明文关键字 |

ABL 关键字符串：

```
IsAllowUnlock is %d
Error Reading FRP partition: %r
Creating unlock keys detect event
Creating fastboot menu keys detect event
No Ffbm cookie found, ignore: %r
ffbm-00 / ffbm-02 / qmmi
Error Reading FFBM info from misc: %r
Boot to FFBM / Boot to QMMI
reboot-fastboot
oem off-mode-charge / device-info / display-cmdline
```

解读：

- **已更正**：FRP 读取与许可位缓存有真实指令依据，但到菜单的完整消费链未闭合；字符串相邻及 Android 属性不能确定 ABL 当时门控值；
- **FFBM/QMMI 由 misc 里的 cookie/命令触发**（`ffbm-00`/`ffbm-02`/`qmmi`）；
  历史 `write_misc` 样本仅改变十进制 73–84 的固定文本字段，前缀为 `recovery\n`；不证明能写 BCB command 或任意偏移，不据此建议写入其它字段或承诺恢复；
- **`fastboot reboot fastboot` 成功进入 fastbootd**（`is-logical` 出现），但
  `getvar all` 太大导致 USB 链路掉线；下次只用短命令（`is-logical:system`、
  `flashing get_unlock_ability`），并且准备好手动重启；
- XBL 确认 **EDL/Sahara 可达**：`DloadCookieAddr = 0x003D3000`、
  `DloadCookieValue = 0x10`、`QCT Root CA`、`OEM_IMAGE_VERSION_STRING=HTSVR18`；
  历史 Sahara 可达；programmer 的完整签名、平台/授权、设备接受与 UFS 仍须逐项验证，不能称 loader 是唯一阻塞。

## 9. ABL 工厂菜单实测（2026-10-26）

关机后 **音量上 + 电源** 进入 ABL 菜单，实际只有：

```
START
Restart bootloader
Recovery mode
Power off
Boot to FFBM
Boot to QMMI
```

- **没有 Unlock 项**：仅为菜单观察，不能反推 FRP 门控值或隐藏原因；
- 选 **Boot to FFBM** → 重启进 Android；
- 选 **Boot to QMMI** → 重启进 Android；

这些结果不能证明 retail 缺少工厂镜像，也未确定回退原因；**该候选路线暂停**。Recovery mode 是原厂 recovery（No command），Restart bootloader 是
fastboot，均无新入口。

结论：**截至历史测试，以上候选未形成可用刷写启动链；不外推所有固件或未测路径。**
当时另列的候选（不代表穷尽所有路线）：
1. **内核写**（GhostLock 5.4.233）→ 写 boot/vbmeta（root/system 是公开 testkey）；
2. **EDL 签名 programmer**（仅 Sahara 可达；签名、授权、设备接受与存储操作均待验证）。
