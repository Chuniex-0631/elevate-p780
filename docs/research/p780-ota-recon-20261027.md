# P780 OTA 情报收集（2026-10-27）

> 目标：在 B 槽（build 264）上只读地找 OTA 端点/包，判断能否拿到 A 槽（build 263）
> 或完整固件，用于恢复/同步 A 槽。结论：**没有可用的公开/本地 OTA 包入口**。

## 1. 已确认 A/B 是不同 build

- 当前系统（B）：`ro.build.fingerprint = .../264:user/release-keys`；
- 原厂 `vbmeta_a.00.bin` 的 prop 描述符：

  ```
  com.android.build.vendor.fingerprint = .../263:user/release-keys
  com.android.build.boot.fingerprint   = .../263:user/release-keys
  ```

  即 **A = 263，B = 264**，A 是上一版，符合 A/B 设备"旧槽保留上一 build"的规律。

## 2. OTA 入口/配置检查（只读）

| 检查 | 结果 |
|---|---|
| `getprop` 中 `ota/update` 相关 | 只有 `ro.build.ab_update=true`、`init.svc.update_engine=running`，无 OTA URL |
| `/system/etc/init/update_engine.rc` | 仅 `update_engine --logtostderr --logtofile --foreground`，无 URL |
| `/system/etc`、`/vendor/etc` 中含 http(s) 的 OTA 配置 | 未发现 |
| OTA 相关包 | `pm list packages` 无 OTA/FOTA/SystemUpdate 应用；只有 Rakuten ecare/feed/launcher 等 |
| `update_engine` 日志中的 URL | 只有我们本轮注入的 `http://127.0.0.1:8080/...`，没有厂商 URL |
| `/data/ota_package` | shell 与 system_app 均 Permission denied |
| `/data/misc/update_engine` | shell 与 system_app 均 Permission denied |
| `/system/etc/security/otacerts.zip` | 只有 vendor 的 `releasekey.x509.pem`（RSA-2048，非 testkey） |

Rakuten 官方页面（[software/rakuten-hand-5g](https://network.mobile.rakuten.co.jp/information/software/rakuten-hand-5g/)）
只给"设置 → 系统更新"的操作说明，不提供 OTA 包下载地址。

## 3. 为什么拿包没有帮助

- 即使拿到 OTA，包是 **release key（RSA-2048）** 签名的，不能改成 rooted；
- 最新 OTA 只包含 **264 及之后**的 boot，不会包含 A 槽的 **263** boot；
- 要恢复 A 的 263，需要**历史 OTA/工厂包**，公开渠道没有；
- 我们已有 update_engine 验签绕过 + 任意块写，缺的不是"签名能力"，而是 **A 槽 263 的 boot 镜像**和 **slot 元数据写权限**。

## 4. 结论

- OTA 端点/包路线**不可行**；
- A 槽无法恢复为 263 stock，也无法通过 OTA 同步；
- 继续刷机需要：签名 EDL loader、可写 misc 的域、或售后工具；
- **主线切回 6931 target A（selinux_state）**：不依赖 A 槽启动，成功后现有 uid0 shell
  即完整 root。
