# Rakuten Hand 5G P780：QAS → Mink → PFM 研究检查点

日期：2026-10-04（Asia/Shanghai）。本次为本机提供 APK 的静态分析，没有连接手机、写入许可证或更改解锁状态。

## 结论

QAS_DVC_MSP.apk 的已定位业务路径为 eMBMS 功能许可检查。固定 PFM class ID=119、feature ID=700；查询结果影响 LTE 广播中间件初始化。当前没有发现这一 Java 调用链到 OEM Unlock、FRP 或 Bootloader 状态写入的连接。此结论限定于已分析文件及可见调用，不等于证明整个 PFM/TEE 不存在其他能力。

QAS 作为 OEM 解锁入口应降低优先级；继续研究的证据缺口在 TZAccessService 服务端、Mink 原生库和实际 PFM 服务实现。不能因同用 TrustZone 或出现 OEMID/PKHASH 字样，就将功能授权视为 Bootloader 授权。

## 已定位调用链

1. LTEBCInitManager.handlePermissionResult(true) 调用 LTELicenseManager.startLicenseCheck(callback, startupReason.ordinal(), context)。ALARM 分支走另一条初始化路径。
2. APP_LAUNCH 可以复用 SharedPreferences 的 LicenseValidity=true；BOOT 或未缓存的 APP_LAUNCH 执行 processLicenseCheck。
3. processLicenseCheck 创建 MinkSocketFd(context, listener)，其 mRemoteSocket=null。
4. MinkSocketFdInternals.connect 以 action com.qualcomm.qti.qms.service.trustzoneaccess.TZAccessService、package com.qualcomm.qti.qms.service.trustzoneaccess 调用 bindService(...,1)。
5. ServiceConnection.onServiceConnected 调用 IMinkSocketFd.request(null, openerHandle[])，取得 ParcelFileDescriptor；nativeCheckFd 后通过 nativeGetMinkOpener(detachFd(), openerHandle[0]) 得到 CMinkObject。
6. LTELicenseManager$1.onConnect：IClientEnv.Proxy.open(119, object[1]) → IPFM.Proxy。
7. 固定执行 CheckInstalledLicense(700, null, byte[1][], 30)。构造器将 700 明确命名为 EMBMS_FEATURE_ID。
8. IPFM.Proxy 将 feature ID 编成 4 字节 little endian，将第二参数作为第二输入 buffer；操作号 1，输出 buffer 大小为 30。30 不是解锁参数或超时秒数。
9. CMinkObject.invoke → nativeInvoke。Java 路径到此进入原生层；该 APK 不含 lib/ 下的 .so，加载库名为 mink-sock-native-api。
10. 查询正常返回后置 licenseValidity=true；notifyLicenseResult 写入该应用自己的 SharedPreferences（com.qti.ltebc.preference / LicenseValidity），通知 LTEBCInitManager。
11. 回调 true 后 connectToEmbms；false 后 LICENSE_STATE_INVALID、LTEBC_INIT_LICENSE_ERROR，可能报 Broadcast not Licensed 或停止中间件。

关键常量及调用已用 DEX 指令复核，避免仅依赖 DAD 反编译的变量类型和异常结构。

## QAS / XRVD 对照

| 项目 | QAS_DVC_MSP | XRVD |
|---|---|---|
| PFM class ID | 119 | 119 |
| CheckInstalledLicense feature | 700，EMBMS_FEATURE_ID | 2100，FEATUREID_XR_2D |
| 第二输入 buffer | null | 调用方 APK 签名证书字节的 SHA-256 |
| 输出 buffer 大小 | 30 | 1024 |
| InstallLicense 业务调用 | DEX 直接引用分析未发现 | installLicense(String) → pfm.InstallLicense(p14.getBytes(), ...) |
| 观察到的用途 | eMBMS 中间件许可 | XR 功能许可 |

QAS 包含 InstallLicense、SetOptions、RemoveLicense 等 IPFM 接口/代理/分发模板。其 Proxy 的 InstallLicense、SetOptions 没有 DEX 直接调用方；IPFM 接口上看到的引用来自通用 MinkObject.invoke 分发模板，不是安装许可证的业务证据。此前字符串检索“installLicense 只在 XRVD”必须保留大小写和语义区别：QAS 内确有大写 InstallLicense 字符串。

XRVD 的 installLicense 接口接收字符串字节，不能由此认定任意字符串会获服务端接受，也不能认定许可证可改变 OEM Unlock。当前没有证明普通第三方客户端能取得任意 PFM 能力或绕过服务端校验。

## 导出组件与输入边界

QAS manifest：四个服务 LTEGroupCallServiceSystem、LTEBroadcastServiceSystem、LTEFileDeliveryServiceSystem、com.qti.ltebc.LTEMSDCService 显式 exported=true；LTERootService=false；三个 receiver 显式 exported=true。lteBroadcastManager 有 MAIN filter，未显式写 exported。

manifest 的 application / 上述服务节点未声明统一入口 permission。但服务导出和没有 manifest permission，不足以证明业务调用不作校验，更不足以证明可任意调用 PFM。

本次完整 DEX 的 IPFM Proxy 直接引用分析只找到一个 CheckInstalledLicense 业务调用点。该点的 class ID、feature ID、null 输入和输出长度均为常量；没有找到将外部 Intent extra 映射为这些参数的路径。业务调用方只有 LTEBCInitManager.handlePermissionResult。故即便外部可触发初始化，也只能据此说明可能触发固定 eMBMS 查询，不能推出可查询/写入任意许可证。

## 额外发现与局限

- processLicenseCheck 中 connect() 返回 false 时，代码确实将本地 licenseValidity=true 并通知成功；DEX 偏移 0x90–0x98 复核。连接成功后的错误回调、1 秒定时器超时则置 false。此处是应用层放行分支，不是 PFM 授权成功，也不是 OEM 解锁。抛异常与返回 false 不能混同。
- APP_LAUNCH 的本地许可缓存可跳过当次 PFM 检查；看见 LicenseValidity=true 日志不代表刚刚完成 TEE 检查。
- 配置复制逻辑含 embms_license.cer 文件名和 MD5 比较特殊处理。当前 CheckInstalledLicense 调用并未读取该证书并传入；不能将文件复制等同于调用 PFM.InstallLicense。MSP native 层行为未审计。
- 查阅完整 DEX 的相关字符串与已定位业务源码，没有看到 OemLockManager、PersistentDataBlockManager、sys.oem_unlock_allowed 或 ro.oem_unlock_supported 连接。字符串阴性并不能排除 native、反射或跨进程间接行为。
- TrustZoneAccessService 的 dumpsys requested permissions 是它自己申请的权限，不是客户端必须持有的 bind/request 权限。queryable via interaction 也不是服务端授权白名单。
- DAD 反编译 Java 可能有变量类型/异常控制流伪影，不应当作能直接编译的原源码。关键行为用附录的 DEX 指令确认。
