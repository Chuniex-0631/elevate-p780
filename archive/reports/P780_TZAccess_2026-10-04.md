# P780：TZAccessService 服务端 Java 授权链

日期：2026-10-04（Asia/Shanghai）。来源：用户上传 hand5g_TZAccessService.apk。本轮完整反编译 APK 的 Java 类，并用 DEX 指令复核 request 分支与凭据采集。未连接手机。

## 关键发现

1. 服务加载 libnative-api.so，APK 内不含该原生库。
2. manifest 的 application/service 没有声明 android:permission；service 有 intent-filter，targetSdk=29，未显式写 exported。onBind 直接返回 IMinkSocketFdImpl。不能据此推断下游无授权。
3. request(String remoteSocket, int[] outHandle) 使用 Binder.getCallingUid()/getCallingPid() 调用 CredentialHelper，并用 PackageManager.getNameForUid 获取调用者名称。
4. CredentialHelper.readConfig 读取准确路径 /vendor/etc/ssg/tz_whitelist.json。
5. getWhitelist 遍历 JSON 的 whitelist 数组，每项读取 permissions 和 classId。调用者必须已获授该项列出的全部权限，才把 classId 加入结果。不是仅检查 manifest 声明；判断 requestedPermissionsFlags & 2。
6. 空 permissions 数组在此 Java 算法中会匹配；配置缺失、读取/解析失败时返回空 int[]。空白名单在 native/后端的实际含义尚未确定，不能等同“允许所有”或“全部拒绝”。
7. QAS/XRVD 的既有 MinkSocketFd 默认传 null，因此走 nativeGetEnvHandle(remoteSocket, callerName, credentials, whitelist)。

## request 路由（已用 DEX 复核）

| remoteSocket | JNI 路径 |
|---|---|
| null 或空字符串 | nativeGetEnvHandle |
| 包含 ssgtzd | nativeGetEnvHandle |
| 包含 qwes_ipc | nativeGetEnvHandle |
| 其余非空字符串 | nativeGetOpenerHandle(remoteSocket) |

DEX 方法内偏移：0x6a 检查空字符串；0x76 检查 ssgtzd；0x86 检查 qwes_ipc；0x98 调用 nativeGetOpenerHandle；0xa2 调用 nativeGetEnvHandle。

注意 DAD 的 qwes_ipc 分支反编译不完整，不能据反编译伪影误判为空操作。另一路径确实没有在 JNI 参数中传入 credentials/whitelist，但这不证明可绕过授权：native 实现、可连接端点及后端策略均未审计。不做任意 socket 试探。

## CBOR 凭据

| 数字键 | 内容 |
|---|---|
| 1 | 真实 Binder 调用 UID |
| 6 | System.currentTimeMillis() |
| 2 | ApplicationInfo.flags |
| 3 | 包名 |
| 4 | X.509 签名证书 getEncoded() 字节数组列表 |
| 5 | 已获授 Android 权限列表 |

UID 非负时基础字段为 1/6。只有 UID 10000～19999 进入应用详细信息分支；UID 1000 的 XRVD 因而不走该分支。getWhitelist 则是独立调用，不能据此推断 UID 1000 自动豁免白名单或一定不受授权控制。

这里的键 4 是完整编码证书，不是 XRVD 在 CheckInstalledLicense(2100,...) 中另行计算的 SHA-256 摘要。两处处理不能混淆。

外部 request 参数不直接接收调用者 UID/签名/权限；这些信息由服务根据 Binder 身份和 PackageManager 构建。这里解决了上一轮仅凭 socket 对端身份无法说明实际 Binder 调用者的证据缺口。

## 对研究方向的影响

目前已经证实 XRVD 的 open(119) 成功；本 APK 进一步揭示 class ID 白名单与调用者凭据如何进入 native 边界。还没有证明 PFM(119) 是白名单配置显式允许、由特定 UID 特判、还是后端其他策略允许。

下一步最有价值的输入为 tz_whitelist.json 和 libnative-api.so。应先判断 119 的权限项以及其他 class ID 的配置，再核对 nativeGetEnvHandle 和 nativeGetOpenerHandle 的实现。

没有发现本 APK Java 代码直接调用 OEM Unlock。PFM 的功能许可与 Bootloader 授权仍未建立关联。
